00文档说明与关键结论

本方案依据客户提供的三份资料编写：《需求.txt》（6 条业务需求）、《明源云数据模板.xlsx》（付款申请明细视图，26 个字段）、《银行账户信息表.xlsx》（9 家法人、41 个账户、39 条农行多级账簿）。方案目标不是再建一套网银，而是在现有采集与对账平台上，把「付款单据 → 账户 → 出纳 → 制单 → 回单」这条链路打通。

本版按客户 2026-11-05 的澄清和《采集明源云审批过程.py》的实测结果修订了四处前提：收款账号在明源云系统内，只是当前导出模板没有取；合同付款申请详情页的「审批过程」弹窗已能返回收款单位开户行、收款单位银行账户和付款单位开户行，可在同一浏览器上下文自动采集；明源云是业务系统、以工程款支付为主，OA 是内部管理系统、承载费控流程，两者是分工而非重复；农行每一个子账簿对应一个付款项目，必须在付款与制单中体现。这四条直接改变了数据接入方式、账户主数据的建设顺序和单据模型。

需要先说明的是：这批资料反映的核心诉求是付款操作层面的协同与制单效率，与前一版《城投地产司库平台建设方案》中「一期只查询、不支付」的边界不同。本方案是司库平台的支付协同专篇，定位为「二期前置」：先把单据、账户、出纳、制单四件事做实，再决定是否进入银企直连。

方案主线：单据统一入库 → 收款账户库补齐 → 业务确认收付款账户 → 按账套分派出纳 → 出纳审核确认可制单 → 生成银行制单批次 → 网银授权支付 → 回单采集与核销。平台做到「待授权」为止，不保存支付授权、不自动提交支付。

七条关键结论

结论依据与影响
收款字段可采集，优先接接口明源云详情页的「审批过程」弹窗已返回收款单位开户行、收款单位银行账户、付款单位开户行，采集脚本已实测；「付款申请明细视图」只是没取这些列。一期优先做自动采集并沉淀收款账户库，Excel 作为兜底；联行号仍需补字段或按开户行映射。
账户性质决定付款权限41 个账户中，贷款户 16 个、监管户 6 个；真正可付款的是 19 个基本户 / 一般户。贷款户按需求明确「不付款、只取回单」，必须在系统里做硬拦截，而不是靠人记。
农行子账簿必须逐笔体现农行 1 个总户挂 39 条多级账簿（1 条主账簿 + 37 个项目账簿 + 1 条归集账簿），一条子账簿对应一个付款项目。付款单据、制单文件、流水归集三处都要体现子账簿，否则项目资金归集会失真。
建行可以先形成闭环仓库中已有建行流水 / 回单采集与批量制单脚本（payment_creator.py），支持生成建行标准批量转账模板并在网银「保存制单」。一期可先用建行跑通全链路，其余 5 家先走标准清单导出。
明源云与 OA 是分工明源云是业务系统，主要承载工程款、合同付款；OA 是内部管理系统，承载费控与费用类付款。两类单据共用一套付款模型，但字段、校验、收款对象和审批链不同，导入模板必须分开。
按账套分派出纳是数据权限问题「按公司账套分配相关账套出纳」不只是角色设置，而是「待办路由 + 数据可见范围 + 操作留痕」三件事，必须用账套维度隔离，不能共用账号。
平台只做到「待授权」UKey 授权、复核、大额联签留在银行侧完成。平台负责把单据和批次准备正确、把结果和回单收回来，避免把支付授权能力引入系统。

02建设目标与范围

2.1 总目标

建设一套付款业务协同与出纳制单工作台，让每一笔付款都能回答五个问题：这笔钱是哪张单、付给谁、从哪个账户付、谁审的、付完有没有回单。目标是一单到底、账实可核，而不是把网银功能搬进平台。

2.2 目标与验收口径

#目标验收口径
1单据统一入库明源云与 OA 单据均可导入；同一来源同一申请编号不重复入库；导入失败可定位到行与字段
2账户可确认付款账户按付款单位与账号自动带出，匹配率 100%；明源云接口单据的收款账户随单返回，匹配率 100%；OA 费控类 ≥ 85%，其余可人工补录并沉淀到账户库
3出纳按账套作业出纳只能看到授权账套的单据与批次；越权访问为 0；待办按账套路由
4审核与制单可控贷款户付款拦截 100%；审核后修改账户必须重回审核；每笔状态与操作可追溯
5制单可落地建行批次生成与网银「保存制单」成功率 ≥ 95%，金额差错为 0；其余银行可导出标准清单
6回单可核销付款流水与回单 T+1 匹配率 ≥ 90%；未匹配项有清单、有责任人、有跟进状态

边界原则：平台负责「把正确的付款准备好」，银行负责「把钱付出去」。这条边界既降低合规风险，也让一期可以在 10–13 周内交付，而不是被银企直连的安全评估拖住。
支付边界：平台只负责把付款单据准备成“制单草稿 / 批次文件”，最终状态是“已制单、待银行复核”。银行侧的复核、授权、支付不由平台承担；银行流水和回单回来后，平台只做匹配与核销。

2.4 设计原则

  • 单一事实源：一张付款申请在平台只有一条主记录，明源云与 OA 通过来源字段区分，不各建一套表。
  • 账户性质驱动：能不能付、能不能自动制单，由账户性质与付款开关决定，不由操作人经验决定。
  • 最小授权：业务只确认账户，出纳只审自己账套，复核只复核批次；权限按账套收窄。
  • 平台内确认：业务确认账户与出纳确认可制单分离；银行侧的复核与授权在网银完成。收款账户变更、贷款户例外、大额付款必须二次确认。
  • 全链路留痕：导入、匹配、调整、审核、制单、支付、核销，每一步都有操作人、时间、前后值。
  • 复用底座：租户、法人、账户、UKey、Agent、任务、流水、回单、对账、审计全部复用现有平台。

  • 批次合计金额必须等于明细合计，生成前做一次全量校验。

9.2 内控要点

  • 四眼原则：业务确认与出纳审核分离；平台只到“确认可制单/制单草稿”，银行复核与授权由银行网银完成。
  • 账户硬控制：贷款户禁止付款；监管户默认禁止自动制单；账户停用后不可再选。
  • 收款人变更：与历史账户不一致时，必须填写原因并二次确认；高风险客户可要求电话核实记录。
  • 金额校验：单据金额、批次合计、银行回单金额三方一致；差异必须说明。
  • 重复付款防护：幂等键 + 相似单据告警 + 原单关联，避免同一申请重复制单。
  • 操作留痕：导入、调整、审核、制单、导出、授权结果全部记录，日志不可删除。
  • 导出管控：付款清单与批次文件属于敏感数据，导出需授权并记录导出人、时间、用途。

9.4 合规与审计

  • 明源云与银行采集器的账号、Cookie、ct 头、Token 必须加密存储，禁止硬编码在源码或提交到仓库；采集账号按最小权限分配并定期轮换。
  • RPA 操作网银需客户书面授权，明确操作范围、账号、时间窗与责任人；建议保留操作录屏或截图。
  • 平台不保存 UKey PIN 的明文，凭据加密存储；制单账号与复核账号分离。
  • 付款数据按角色脱敏展示，账号默认只显示后四位，导出需二次确认。
  • 审计日志、批次文件、回单按客户要求保留，满足国资与内审追溯。
  • 上线前完成权限矩阵演练、越权测试与数据迁移核对。
